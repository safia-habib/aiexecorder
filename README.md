# State AI EO Explorer

An interactive map of the US that shows each governor's AI-related executive order and which
Dynatrace, Bindplane, and Arize capabilities help that state's agencies comply — answers
generated by a RAG pipeline backed by Azure OpenAI.

---

## Architecture

```
                         ┌──────────────────────────────────────────────────┐
                         │            ai-eo-explorer  (k8s namespace)        │
                         │                                                    │
  Browser ──► Ingress ──►│ /        ──► frontend (nginx, :80)                │
              (or LB IP) │               │  serves React SPA                  │
                         │ /api ────────►│                                    │
                         │              └──► backend (FastAPI, :8000)         │
                         │                    │  GET /api/states              │
                         │                    │  GET /api/states/{code}/eo    │
                         │                    │  POST /api/ask  (SSE stream)  │
                         │                    │                               │
                         │                    └──► qdrant (:6333)             │
                         │                         vector store (PVC: 5 Gi)   │
                         └──────────────────────────────────────────────────┘
                                    │ (external)
                         Azure OpenAI API
                           ├── text-embedding-3-small  (embeddings)
                           └── gpt-4o                  (chat completions, streamed)

RAG flow (POST /api/ask):
  question ──► Azure OpenAI embed ──► Qdrant similarity search (filtered by state_code)
           ──► top-3 chunks as context ──► gpt-4o chat completion ──► SSE token stream ──► browser
```

**Design choices:**
| Decision | Choice | Reason |
|---|---|---|
| Embeddings | Azure OpenAI `text-embedding-3-small` | 1536-dim, high quality, no self-hosted GPU needed |
| LLM | Azure OpenAI `gpt-4o` with streaming | Fast, accurate, SSE-compatible via `stream=True` |
| RAG orchestration | Plain Python (no LangChain/LlamaIndex) | One Qdrant search + one Azure OpenAI call; no framework overhead |
| Chunking | One primary chunk per state + optional field chunks for long text | Simple retrieval; always returns the full state record for context |
| Observability | OpenInference semantic conventions on every RAG span | Arize Phoenix / Dynatrace / any OTLP backend; disabled when `OTLP_ENDPOINT` unset |

## Local development (Docker Compose)

### 1. Configure Azure OpenAI credentials

```bash
cp backend/.env.example backend/.env
```

Edit `backend/.env` and fill in your Azure OpenAI details:

```env
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_API_KEY=<your-api-key>
AZURE_OPENAI_API_VERSION=2024-12-01-preview
AZURE_OPENAI_DEPLOYMENT=gpt-4o
AZURE_OPENAI_EMBEDDING_DEPLOYMENT=text-embedding-3-small
```

You can also export these as shell environment variables — docker-compose will pick them up automatically.

### 2. Start the stack

```bash
docker compose up -d
```

This starts Qdrant and the backend (which reads credentials from `backend/.env` or host env vars), plus the nginx frontend.

### 3. Run ingestion (first time and after spreadsheet updates)

```bash
docker exec -it ai-eo-backend \
  python -m ingestion.ingest \
    --data-path /data/State_AI_Executive_Orders_Dynatrace_Report.xlsx \
    --recreate
```

You will see one line per state confirming how many chunks were embedded and upserted.
When it prints `Done. Ingested N state(s), M total chunk(s)` the data is live in Qdrant.

### 4. Open the app

- **Frontend (nginx/built):** http://localhost:3000
- **Backend API docs (Swagger):** http://localhost:8000/docs

### 5. Run the unit tests (no running services required)

```bash
cd backend
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS / Linux
pytest -v
```

## Kubernetes deployment (EKS / GKE / AKS)

### Prerequisites

- `kubectl` configured against your cluster (`kubectl cluster-info` succeeds)
- Docker and a container registry (ECR, GCR, or ACR) your cluster can pull from
- An **Azure OpenAI resource** with two deployments provisioned:
  - A chat model — e.g. `gpt-4o` (set as `AZURE_OPENAI_DEPLOYMENT`)
  - An embedding model — e.g. `text-embedding-3-small` (set as `AZURE_OPENAI_EMBEDDING_DEPLOYMENT`)
- Nodes need only normal CPU/RAM (≥ 2 vCPU, ≥ 4 GB per pod) — no GPU required

---

### Step 1 — Add your Azure OpenAI credentials

**Secret (API key)** — edit [k8s/secret-stub.yaml](k8s/secret-stub.yaml):

```yaml
stringData:
  AZURE_OPENAI_API_KEY: "your-actual-api-key-here"
```

**ConfigMap (endpoint + deployment names)** — edit [k8s/configmap.yaml](k8s/configmap.yaml):

```yaml
data:
  AZURE_OPENAI_ENDPOINT: "https://<your-resource>.openai.azure.com/"
  AZURE_OPENAI_DEPLOYMENT: "gpt-4o"
  AZURE_OPENAI_EMBEDDING_DEPLOYMENT: "text-embedding-3-small"
  AZURE_OPENAI_API_VERSION: "2024-12-01-preview"
```

> **Important:** Do not commit `k8s/secret-stub.yaml` with a real API key.
> For production, use a sealed-secret, Key Vault CSI driver, or similar.

---

### Step 2 — Set the Qdrant storage class

Open [k8s/qdrant/pvc.yaml](k8s/qdrant/pvc.yaml) and uncomment `storageClassName`:

| Cloud | Recommended class |
|---|---|
| EKS | `gp3` |
| GKE | `standard-rwo` (HDD) or `premium-rwo` (SSD) |
| AKS | `managed-csi` (HDD) or `managed-premium` (SSD) |

Leave unset to use the cluster's default.

---

### Step 3 — Build and push both images

```bash
# Set your registry prefix once
REGISTRY=<your-registry>   # e.g. 123456789.dkr.ecr.us-east-1.amazonaws.com/ai-eo

# Run both builds from the repo root (not from backend/ or frontend/)
# The backend Dockerfile uses the repo root as context so it can include data/
docker build -f backend/Dockerfile -t ${REGISTRY}-backend:latest .
docker build -f frontend/Dockerfile -t ${REGISTRY}-frontend:latest ./frontend

docker push ${REGISTRY}-backend:latest
docker push ${REGISTRY}-frontend:latest
```

Then update the two `image:` lines:
- [k8s/backend/deployment.yaml](k8s/backend/deployment.yaml) — replace `your-registry/state-ai-eo-backend:latest`
- [k8s/frontend/deployment.yaml](k8s/frontend/deployment.yaml) — replace `your-registry/state-ai-eo-frontend:latest`

---

### Step 3 — Deploy with the deploy script (recommended)

[`deploy.sh`](deploy.sh) applies resources in dependency order and waits for each
component to be healthy before moving on:

```bash
chmod +x deploy.sh
./deploy.sh
```

The script walks through eight steps automatically:

| Step | Resources | Wait condition |
|------|-----------|----------------|
| 1 | Namespace | Active |
| 2 | ConfigMap + Secret | — |
| 3 | Qdrant PVC + StatefulSet + Service | Pod Ready (2 min) |
| 4 | Backend Deployment + Service | Rollout complete (3 min) |
| 5 | `run-ingestion` Job | Job Complete — calls Azure OpenAI to embed all EO records (~2–5 min) |
| 6 | Frontend Deployment + Service + LoadBalancer IP | Rollout + IP assignment (3 min) |
| 7 | Ingress | — |
| 8 | Summary | Prints `kubectl get all` + public URL |

**Flags:**

```bash
./deploy.sh --skip-models    # skip model pull when weights are already in the Ollama PVC
./deploy.sh --namespace foo  # deploy into a different namespace (default: ai-eo-explorer)
```

**Alternative — apply everything in one shot (no readiness checks):**

```bash
kubectl apply -k k8s/
```

This creates in one shot: namespace, PVCs, Qdrant StatefulSet, Ollama StatefulSet,
backend Deployment, frontend Deployment, the model-pull Job, and the Ingress stub.
Use this only if you prefer to monitor pod readiness yourself.

### Step 5 — Run ingestion

Port-forward Qdrant and Ollama to your local machine, then run the ingestion

the spreadsheet off the cluster entirely.

# Terminal A
kubectl port-forward -n ai-eo-explorer svc/qdrant 6333:6333

# Windows PowerShell

### Step 6 — Accessing the app via public IP

The frontend service is configured as `type: LoadBalancer`. Your cloud provider
automatically provisions a public IP or hostname. `deploy.sh` waits for it and
prints it — but you can also fetch it at any time:

```bash
kubectl get svc frontend -n ai-eo-explorer
# NAME       TYPE           CLUSTER-IP     EXTERNAL-IP      PORT(S)        AGE
# frontend   LoadBalancer   10.0.12.34     203.0.113.42     80:31234/TCP   2m
```

Open **`http://<EXTERNAL-IP>`** in your browser — no port-forwarding needed.

The backend stays on `ClusterIP` (internal only). The nginx inside the frontend
container proxies `/api` to `http://backend:8000` within the cluster, so the
backend is never exposed to the internet.

#### Cloud-specific annotations (optional)

Uncomment the relevant block in [k8s/frontend/service.yaml](k8s/frontend/service.yaml)
before applying if you need to control load balancer behaviour:

| Cloud | What to uncomment |
|---|---|
| **EKS** | `aws-load-balancer-type: external` + `scheme: internet-facing` + `nlb-target-type: ip` |
| **GKE** | No annotation needed — external L4 LB is the default |
| **AKS** | No annotation needed — standard public LB is the default |

#### Ingress (optional — for custom domains / TLS)

If you later add a custom domain or need TLS termination, use
[k8s/ingress.yaml](k8s/ingress.yaml) instead. Uncomment the nginx annotation
block, set `ingressClassName: nginx`, and revert the frontend service to
`ClusterIP`:

```bash
kubectl apply -f k8s/ingress.yaml
```

| Controller | SSE streaming | Notes |
|---|---|---|
| **nginx Ingress** | Fully supported (`proxy-buffering: off`) | Recommended for production |
| **AWS ALB** | Works; set idle timeout ≥ 600 s | Native via aws-load-balancer-controller |
| **GKE managed Ingress** | May buffer SSE | Non-streaming use only |

## Troubleshooting

| Symptom | Check |
|---|---|
| `backend` pod stuck in `Init:0/1` | Init container waiting for deps. Run `kubectl logs -n ai-eo-explorer <backend-pod> -c wait-for-deps`. Likely Qdrant or Ollama not ready yet. |
| `ollama-0` Running but models missing | Job `ollama-pull-models` may have failed. Check `kubectl logs -n ai-eo-explorer -l job-name=ollama-pull-models`. Re-run the pull job by deleting and reapplying it. |
| `/api/health` shows `"ollama": "unreachable"` | Ollama pod isn't ready. Models may still be downloading. Wait for the pull-models job to Complete. |
| `/api/health` shows `"qdrant": "unreachable"` | Qdrant pod crashed or PVC not bound. Check `kubectl describe pod qdrant-0 -n ai-eo-explorer`. |
| `/api/states` returns all `has_eo: false` | Ingestion has not been run yet, or ran against a different Qdrant collection. Re-run ingestion with `--recreate`. |
| SSE streaming cuts off early | Ingress or load balancer buffering responses. Use nginx Ingress with `proxy-buffering: off` (see Step 6). |
| OOM on Ollama pod | Node has less than 14 GB allocatable memory. Resize the node, or provision a GPU node pool and uncomment the GPU blocks in [k8s/ollama/statefulset.yaml](k8s/ollama/statefulset.yaml). |
| `state_code not found` for a state | The `State` column value in the spreadsheet doesn't exactly match a known state name. Check `normalize_state_code` output during ingestion for the WARNING line. |

## How RAG answers are grounded in the spreadsheet data

The backend never calls an external knowledge base or the LLM's parametric memory
for policy facts. Every answer is produced as follows:

1. **Ingestion** reads the spreadsheet one row at a time. Each row is formatted as a
   structured text block (all nine fields) and embedded with `nomic-embed-text`.
   Only data from the spreadsheet is stored in Qdrant — no web scraping, no
   supplemental sources.

2. **At query time**, the user's question is embedded with the same model, and Qdrant
   runs a cosine-similarity search **filtered to the selected state's `state_code`**.
   This means the retriever can only surface chunks from that one state's record.

3. **The system prompt** passed to `llama3.1:8b` explicitly instructs the model:
   > "Answer based ONLY on the provided context. If the context does not contain
   > enough information to answer, say so clearly. Do not invent policy details
   > not present in the context."

4. **States with no ingested data** cause the retriever to return an empty result set.
   The backend detects this and returns a fixed refusal message
   (`"No executive order data is on file for {state}. I cannot answer this question."`)
   without ever calling the LLM. The LLM is never given an opportunity to hallucinate
   for unknown states.

5. **Updating the source** — if the spreadsheet changes, re-run ingestion with
   `--recreate` to rebuild the collection from scratch. No frontend changes are needed;
   the backend reads live from Qdrant on every request.
